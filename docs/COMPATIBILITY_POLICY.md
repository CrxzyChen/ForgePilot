# Studio and project compatibility policy

Round 02 uses an explicit compatibility set rather than resolving the newest
available tool at runtime. A project is portable; Studio owns the mapping from
stable project commands to the installed binaries.

## Current compatibility set

| Surface                   | Supported value                       | Enforcement                                     |
| ------------------------- | ------------------------------------- | ----------------------------------------------- |
| Studio                    | `0.1.1`                               | Electron application and build manifest version |
| Project format            | `1.0.0`                               | `project.aigame.json` parser and JSON Schema    |
| Game IR / engine protocol | `1.0.0`                               | native kernel validation and replay             |
| Template layers           | exact recorded `1.0.0` lineage        | composer and project manifest                   |
| Codex App Server          | exact `0.152.1`                       | bundled-package resolver and clean-path gate    |
| Codex protocol bindings   | output generated by bundled `0.152.1` | byte-for-byte drift check                       |
| Electron                  | exact `44.1.1` dependency             | lockfile and packaged runtime manifest          |
| Engine MCP                | MCP `2025-06-18`, server `0.1.1`      | Project Doctor handshake and tool discovery     |

The Studio package contains its compatible Codex Windows binary and only uses
that package in the normal desktop path. It never silently falls back to a
global Node.js or Codex installation. Studio prepends its private `bin`
directory when starting Codex, so `.codex/config.toml` can keep the portable
command `aigame-mcp --project .` without a machine-specific path.

## Compatibility decisions

- Patch releases may open the same project format without migration when all
  schemas and semantic behavior remain compatible.
- A project-format, Game IR, or template-lineage change requires an explicit,
  previewable migration. Studio keeps the original bytes until the migrated
  project validates and the user approves the ChangeSet.
- An unsupported newer format is rejected; Studio must not guess or downgrade
  it. An older supported format opens read-only until its migration succeeds.
- Codex App Server and generated bindings advance as one reviewed change. The
  protocol drift check must pass before packaging.
- Studio verifies the sidecar version before launch. A missing or mismatched
  package is a repairable Studio diagnostic, not a reason to search the user's
  PATH.
- Engine MCP declares its protocol and tool inventory during Project Doctor.
  Missing required tools prevent the first Agent turn.

## Update, rollback, and support window

Studio updates are staged outside the running installation, hashed, and become
active only after package verification. A failed launch or compatibility gate
keeps the previous installation selectable. Round 02 supports the current
compatibility set and the immediately preceding project format once the first
migration exists; no earlier compatibility is implied yet.

Project upgrades create a Git checkpoint when Git is available and always keep
a transaction journal. Template upgrades use a three-way merge and never
overwrite project-authored files silently. Game release packages pin their
runtime and are not changed by a Studio update.

## Release evidence

`STUDIO-BUILD-MANIFEST.json` records the Electron and Codex versions, every file
hash, global-runtime requirements, and the clean-path P8 result. Packaging
launches the produced `AI Game Studio.exe` with a PATH that contains Windows
system tools but no Node.js, npm, Git, or global Codex. That packaged process
must create a project, pass Project Doctor including the Engine MCP handshake,
start the managed App Server, resume or create its project thread, and execute
the initial replay before the package is accepted.
